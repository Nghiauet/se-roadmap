## The big idea

Networking is **layered**, and each layer adds one capability the one below didn't have.
The trick to learning it is *not* memorising OSI's seven layers — it's understanding the
four you actually touch.

## A request, layer by layer

When you type `https://example.com` in a browser:

<Steps>
  <Step title="DNS resolution">
    Your machine asks a recursive resolver for the `A`/`AAAA` records of `example.com`.
    Cached almost everywhere — DNS is mostly a cache hierarchy with a tiny authoritative
    base at the bottom.
  </Step>
  <Step title="TCP handshake">
    Your client sends `SYN`, the server replies `SYN-ACK`, you send `ACK`. One round trip
    before you can send any data.
  </Step>
  <Step title="TLS handshake">
    The server presents a certificate; your client verifies it chains to a trusted CA.
    Asymmetric crypto establishes a shared session key, then everything switches to fast
    symmetric encryption.
  </Step>
  <Step title="HTTP request">
    Finally the real conversation happens — over an encrypted TCP stream.
  </Step>
</Steps>

<Callout tone="tip" title="Why HTTP/3 matters">
HTTP/3 swaps TCP for QUIC (which is built on UDP). Connections survive network changes
(Wi-Fi → 4G) and there's no head-of-line blocking. Most CDNs already speak it; your job is
mostly to turn it on.
</Callout>

## Ports, sockets, processes

A **port** is just a 16-bit number used by the OS to route a packet to the right process.
A **socket** is the OS-level handle for one connection: `(local_ip, local_port, peer_ip,
peer_port)`. A web server listens on `(0.0.0.0, 443)`; for each incoming connection, the
OS creates a new socket with a unique peer side.

<Callout tone="info" title="Useful default ports">
HTTP **80**, HTTPS **443**, SSH **22**, DNS **53**, Postgres **5432**, Redis **6379**,
MySQL **3306**. Knowing these by heart saves you from `netstat` half the time.
</Callout>

## TLS in 30 seconds

Every TLS connection achieves three things at once:

<DefinitionList>
  <Definition term="Confidentiality">Nobody between you and the server can read the traffic.</Definition>
  <Definition term="Integrity">Nobody between you can modify it without detection.</Definition>
  <Definition term="Authentication">The server proves it's the legitimate owner of the domain via a certificate signed by a CA.</Definition>
</DefinitionList>

Modern TLS (1.3) cuts the handshake to one round trip, drops weak ciphers, and is what
you should be running. Anything older is a known bug.

## Useful tools

```bash
# DNS — which IPs is example.com on?
dig +short example.com
host -t AAAA example.com

# What's actually listening on this box?
ss -tlnp                  # Linux
lsof -nP -iTCP -sTCP:LISTEN -p 0

# Reach the server at all?
nc -zv example.com 443
curl -v https://example.com    # full TLS + HTTP trace

# What route do packets take?
traceroute -T -p 443 example.com
```

## In practice

A surprising number of "the API is down" tickets are really DNS (resolver cache, expired
record), TLS (expired cert, wrong SNI), or firewalls (port closed in a new VPC). Walk the
layers top-down: HTTP → TLS → TCP → DNS. The first one that fails is your bug.
